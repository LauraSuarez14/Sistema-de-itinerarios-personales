🌱 Resumen ejecutivo

Sistema de Itinerarios Personales es una aplicación académica de planificación de viajes, construida deliberadamente para demostrar tres estilos arquitectónicos combinados: microservicios, arquitectura basada en eventos, y serverless (FaaS). No es un proyecto "de negocio" real, sino un ejercicio de nivel 1+2+3 de un reto de arquitectura de software.

El sistema deja crear/listar/eliminar itinerarios de viaje entre aeropuertos colombianos reales (obtenidos de la API pública API Colombia), y notifica de forma asíncrona cuando se crea uno.

  • Frontend: Angular 18 standalone, con mapa interactivo (Plotly) y CRUD de itinerarios.
  • Backend: 4 servicios Python/FastAPI (Airport, Itinerary, API Gateway, notification-bridge) + 2 funciones Lambda.
  • Infraestructura: PostgreSQL, Redis, RabbitMQ, LocalStack, Vault, Toxiproxy, Jaeger, Prometheus, Grafana — todo vía docker-compose.

🌻 Bounded contexts (DDD) y lenguaje ubicuo

Airport Context

Conoce los aeropuertos colombianos y los expone en un formato de dominio propio, desacoplado de la API externa.

TérminoSignificado
AirportEntidad con id, nombre, código IATA, ciudad, latitud/longitud
AirportRepositoryPortContrato del dominio para obtener aeropuertos, sin saber cómo se implementa
ApiColombiaAdapterTraduce la respuesta externa al modelo de dominio
CachingAirportAdapterDecorador que aplica cache-aside sobre Redis
CircuitBreakerCorta las llamadas a la API externa cuando falla repetidamente

Itinerary Context

Responsable del ciclo de vida de los itinerarios de viaje del usuario.

TérminoSignificado
ItineraryAgregado raíz: usuario, aeropuertos origen/destino (referencia de valor), fecha, duración
CreateItineraryUseCase, etc.Orquesta validación + persistencia + evento de dominio
OutboxEventFila transaccional que garantiza la publicación futura del evento
ItineraryCreatedEvent v1Evento de integración versionado (ver AsyncAPI)

Notification Context

Reacciona a la creación de itinerarios y genera reportes bajo demanda, sin servidor permanente.

TérminoSignificado
SendNotificationFunctionLambda activada al recibir ItineraryCreatedEvent
GenerateItineraryReportFunctionLambda invocada bajo demanda
notification-bridgeTraduce mensajes de RabbitMQ a invocaciones Lambda

Los tres contextos se comunican solo por contratos explícitos — ningún contexto accede directamente a la base de datos de otro.

🌹 Patrón Adapter + Arquitectura Hexagonal

Cada microservicio (Airport, Itinerary) se organiza en las mismas capas, con la regla de dependencia siempre hacia adentro:

flowchart TB API["api/ (routers FastAPI, esquemas Pydantic)"] --> APP["application/ (casos de uso)"] INFRA["infrastructure/ (Postgres, Redis, RabbitMQ, gRPC, HTTP externo)"] --> APP APP --> DOM["domain/ (entidades, value objects, puertos)"]
  • domain/ports.py → interfaz AirportRepositoryPort (el "Puerto")
  • infrastructure/api_colombia_adapter.py → ApiColombiaAdapter (el "Adapter")
  • infrastructure/caching_adapter.py → CachingAirportAdapter (decora al Adapter)

El dominio nunca depende de detalles externos: el frontend y los demás servicios solo conocen el modelo adaptado (REST /api/v1/airports y gRPC airport.v1.AirportService).

Nota de diseño (ADR 0001): Itinerary Service no tiene tabla airports; el aeropuerto se trata como referencia de valor, validada vía gRPC en el momento de creación, y solo se guarda un snapshot inmutable (id, IATA, nombre) para lectura posterior.

🌼 Flujo de eventos: Transactional Outbox

Problema (ADR 0002): escribir en Postgres y publicar en RabbitMQ como dos pasos separados crea una ventana de inconsistencia (Double Write Problem). La solución: insertar el evento en la misma transacción que el agregado, y un proceso en background (OutboxRelay) lo publica después.

sequenceDiagram actor Usuario participant FE as Frontend Angular participant GW as API Gateway participant IS as Itinerary Service participant AS as Airport Service participant MQ as RabbitMQ participant NB as notification-bridge participant LS as SendNotificationFunction Usuario->>FE: Completa formulario FE->>GW: POST /api/v1/itineraries (Bearer JWT) GW->>IS: proxy + propaga Authorization IS->>AS: gRPC GetAirportById x2 (token OAuth2 S2S) AS-->>IS: AirportReply (found=true) IS->>IS: INSERT itinerary + INSERT outbox_event (misma transaccion) IS-->>GW: 201 Created GW-->>FE: 201 Created loop cada OUTBOX_RELAY_INTERVAL_SECONDS IS->>IS: OutboxRelay busca eventos pendientes end IS->>MQ: publish ItineraryCreatedEvent v1 MQ->>NB: entrega el mensaje NB->>LS: lambda Invoke SendNotificationFunction LS-->>NB: status sent / duplicate NB->>MQ: ack

Semántica at-least-once deliberada: el consumidor (SendNotificationFunction) es idempotente — guarda el event_id procesado y descarta duplicados.

🌻 Decisiones arquitectónicas clave (ADRs)

ADR 0001 — Aeropuerto como referencia de valor

Itinerary Context no replica la entidad Aeropuerto completa; valida por gRPC contra Airport Service y guarda solo un snapshot mínimo e inmutable. Consecuencia: un itinerario ya creado sigue siendo legible aunque Airport Service esté caído, pero crear uno nuevo sí lo requiere.

docs/adr/0001-agregado-aeropuerto.md

ADR 0002 — Transactional Outbox

Resuelve el Double Write Problem entre Postgres y RabbitMQ. At-least-once + deduplicación en el consumidor, en vez de 2PC entre BD y broker.

docs/adr/0002-double-write-problem.md

ADR 0003 — Eventos de dominio vs. de integración

ItineraryCreated (dominio, interno, sin contrato) vs. ItineraryCreatedEvent v1 (integración, cruza la frontera del servicio, contrato versionado en docs/asyncapi.yaml).

docs/adr/0003-eventos-dominio-vs-integracion.md

🌷 Seguridad

  • Usuario → sistema: API Gateway emite JWT (HS256) en POST /auth/login (usuario demo: viajero / viajero123, definidos en .env como DEMO_USER/DEMO_PASSWORD) y lo propaga a los servicios internos.
  • Servicio → servicio: Itinerary Service obtiene un token OAuth2 Client Credentials de Airport Service (POST /oauth/token) y lo envía como metadata gRPC; un interceptor gRPC rechaza cualquier llamada sin token válido.
  • Endpoints públicos: GET /api/v1/airports* son públicos a propósito (el mapa funciona sin sesión); invalidar caché sí exige JWT.
  • Secretos: cada servicio intenta leer de Vault al arrancar y cae a variables de entorno si Vault no está disponible.

🌼 Resiliencia y Chaos Engineering

  • Circuit Breaker propio (async, 3 estados) + Retry con backoff exponencial y jitter (tenacity) + Bulkhead (semáforo dedicado) alrededor de las llamadas de Airport Service a la API externa.
  • Cache Redis (cache-aside, con invalidación explícita).
  • Chaos Engineering: TOXIPROXY_ENABLED=true enruta Airport Service a través de Toxiproxy hacia un stub local que imita API Colombia; scripts/chaos_demo.sh inyecta latencia y muestra la apertura del circuit breaker.

Archivo clave: services/airport-service/app/infrastructure/resilience.py

🌻 Observabilidad

  • Trazas distribuidas: OpenTelemetry (FastAPI + httpx + gRPC) exportando a Jaeger.
  • Logs estructurados: JSON con trace_id/span_id/correlation_id (libs/common/common/logging.py + correlation.py).
  • Métricas: Prometheus scrapea los 4 servicios Python + RabbitMQ; alertas en infra/prometheus/alert_rules.yml (circuit breaker abierto, dead-letters, bulkhead saturado); dashboard en Grafana.

🌷 Hallazgos reales al ejecutar el sistema por primera vez

El README original advertía que el flujo Docker nunca se había corrido de punta a punta. Al levantarlo con docker compose up, aparecieron estos bugs reales — muy útiles para entender el comportamiento real del sistema más allá de lo documentado:

1. Conflicto de dependencias pip (airport-service)

grpcio-tools==1.66.1 exige protobuf>=5.26.1, pero opentelemetry-exporter-otlp-proto-grpc==1.27.0 exige protobuf<5.0. Se relajaron los pines de OpenTelemetry a >=.

services/airport-service/requirements.txt

2. Scripts con CRLF (checkout en Windows)

4 scripts .sh tenían saltos de línea CRLF, rompiendo exec en contenedores Linux (no such file or directory). Se corrigieron y se añadió .gitattributes.

services/itinerary-service/docker-entrypoint.sh, infra/localstack/init/01_create_functions.sh, scripts/*.sh

3. Import de FastAPI a nivel de módulo rompía notification-bridge

common/telemetry.py importaba FastAPIInstrumentor arriba del archivo, pero notification-bridge no usa FastAPI (ni lo tiene instalado). Se movió el import dentro de setup_telemetry().

libs/common/common/telemetry.py

4. FastAPI 204 + response_model implícito

Un endpoint DELETE con retorno -> None se infiere como response_model=NoneType, lo cual choca con status 204 ("no debe tener cuerpo"). Se agregó response_model=None explícito.

services/itinerary-service/app/api/routers/itineraries.py

5. vars() sobre un dataclass con slots=True

Airport es @dataclass(frozen=True, slots=True) (sin __dict__); vars(airport) lanzaba TypeError. Se cambió a dataclasses.asdict().

services/airport-service/app/api/routes.py

6. LocalStack 3.8: el ejecutor Lambda "local" está obsoleto

Requiere montar /var/run/docker.sock para el ejecutor Lambda real (Docker-outside-of-Docker); además, ese ejecutor solo permite escribir en /tmp (como en AWS real), así que NOTIFICATION_DB_PATH se movió ahí.

docker-compose.yml, infra/localstack/init/01_create_functions.sh, functions/send_notification_function/handler.py

7. Bug real en el Outbox Relay: bucle infinito de republicación

pika's channel.basic_publish() no devuelve un booleano (devuelve None incluso en éxito); el código hacía return channel.basic_publish(...), así que published_at nunca se marcaba y el evento se reenviaba cada ciclo, para siempre.

services/itinerary-service/app/infrastructure/messaging/rabbitmq_publisher.py

Conclusión para Ximena: el diseño documentado (ADRs, README) es correcto y coherente, pero el código tenía varios bugs de "primera ejecución" nunca detectados porque nadie lo había corrido contra Docker real. Vale la pena revisar el git log reciente para ver el diff exacto de cada fix.
